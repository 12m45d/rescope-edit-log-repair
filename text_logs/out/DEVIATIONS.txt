15. Memory fallback of the public probability test (model.config.use_cache)
   what: The public test_batch_prediction feeds the 46 sequences of a record as one padded batch through model(**batch); with
         the default config the forward also returns the key / value tensors of all 48 layers.  For a record with a very long
         paraphrase prompt this exceeds the memory cap of the queue job (case 1531: a 179-token paraphrase, 46 x 181 tokens;
         first seen as an out-of-memory failure, logs/describe_A_oom_case1531.out).  tp_common.public_prob_test calls the
         public function as is and, on a CUDA out-of-memory error only, calls the same public function again with
         model.config.use_cache = False (the forward then returns no key / value tensors; the logits are computed by the same
         operations).  Records evaluated that way carry prob_test_use_cache_false = true in their case file: description,
         run_T1000: case(s) [147, 427]; description, run_T2000: case(s) [147, 427, 1531, 1878]; description, run_T500:
         case(s) [147, 427]; description, run_W0: case(s) [1531, 1878]; write time, stream: case(s) [1531].  Equality of the
         public function's output under both settings was checked on three records at the pre-edit weight (bit for bit: not
         run yet).
   why : GPU memory is shared; the alternative was a reservation of about 15 GB for one record

16. Generation metric of the description
   what: The public test_generation needs the attribute snippets and the tf-idf vectoriser for its consistency score.  The
         description calls the two public functions it is made of that do not need them: util.generate.generate_fast(model,
         tok, generation_prompts, n_gen_per_prompt=1, max_out_len=100) and eval_utils_counterfact.n_gram_entropy(texts of one
         record).  The generation prompts of 2 records (20 prompts) are passed to one generate_fast call instead of one call
         per record, with torch.manual_seed(77000 + index of the first record) before each call; rows of a batch do not
         interact in generate_fast (no pad position is fed), so only the random numbers drawn differ from per-record calls.
         The consistency (reference) score and the essence score are not computed.  nltk.word_tokenize is that of nltk 3.10.4
         (punkt_tab), not 3.6.5.
   why : the consistency score is not required; a seed makes the sampled generations reproducible and paired across weights;
         one call per record took about 15 minutes per 100 records on the shared cards (a first attempt was stopped for that
         reason)
